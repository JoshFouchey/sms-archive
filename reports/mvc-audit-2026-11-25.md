# Spring MVC / JPA Audit — sms-archive

**Date:** 2026-11-25 · **Commit:** 999b365 · **Auditor:** Copilot (webflux-reactive-audit skill, adapted for a servlet + JPA stack)

> This service is **not reactive** (Spring MVC on Tomcat, JPA/Hikari). The audit keeps the skill's four dimensions, severity scale and grading rubric. The reactive checks were swapped for their servlet equivalents: thread/connection-pool exhaustion instead of event-loop blocking, lost SecurityContext/ThreadLocal instead of lost Reactor Context, transaction/proxy pitfalls instead of subscription bugs, and N+1/unbounded result sets instead of backpressure. Severity is calibrated to how it is actually deployed: self-hosted, 1–3 users, but large data (~200k messages, multi-GB imports, 100k-message threads).

## Executive summary

sms-archive is a Spring Boot 4.1.2 MVC + JPA service that imports Android SMS/MMS backups into Postgres 18/pgvector and serves browse, search and optional llama.cpp-backed AI features. The core read and import paths are thoughtfully built: streaming StAX parse, two-phase paging, batch fetching, idempotent re-imports, and real-Postgres integration tests. The biggest risk is **user isolation and exposure**, not throughput:
- Conversation caches are keyed only by id, so a cache hit skips the ownership check.
- Media files are served with no authentication.
- `/api/qa/sql/run` accepts any SQL that merely *contains* `user_id`.
- Image delete checks no ownership.

With one user these are latent; with a second account or an internet-reachable proxy they are real leaks. The second theme is **resource hygiene under large data**: never-deleted multi-GB upload temp files, a 50k-entity endpoint, unindexable keyword search, and an AI timeout/retry stack that can hold a request thread for minutes when llama.cpp is down. Recommended work: a short isolation sprint (mostly S-effort), then CI test gating, then targeted performance fixes on search and import.

## Top priorities

1. **COR-1 — add the user to the conversation cache keys** (S). One-line key change on 3 `@Cacheable`s; closes a cross-user read.
2. **COR-6 — delete upload temp files after import** (S). Each import leaks a copy of a multi-GB file into the container's /tmp until disk fills.
3. **COR-4 — compare user ids, not `User` instances** (S). Contact rename/merge likely 404 in prod after the first request; also fixes the same pattern anywhere `getUser().equals(user)` is used.
4. **OBS-1 — run `./gradlew test` in the GitHub Actions workflow before pushing `latest`** (S). Every other fix in this list needs a safety net.
5. **COR-20 / COR-2 / COR-3 — close the remaining isolation holes** (M). Authenticated media (signed URLs), DB-enforced scoping for text-to-SQL (restricted role + RLS, or user-scoped CTE wrapping), and an ownership check in `deleteImage`.
6. **RES-1 — short, no-retry budget for query embeddings** (S). Stops hybrid search from hanging for minutes when the embedding server is down.

#### COR-1: Conversation caches keyed only by conversationId bypass the ownership check on cache hits
- **Location:** `src/main/java/com/joshfouchey/smsarchive/service/ConversationService.java:195-260`
- **Dimension:** Correctness · **Confidence:** High
- **What:**

  ```
  @Cacheable(value = "conversationMessages", key = "#conversationId")
  public List<ConversationMessagesDto> getAllConversationMessages(Long conversationId) {
      var user = currentUserProvider.getCurrentUser();
      conversationRepository.findByIdAndUser(conversationId, user)...
  // same pattern: conversationMessageCount (236), conversationTimeline (248)
  ```
- **Why it matters:** The Spring cache interceptor runs before the method body. Once user A has loaded conversation N, a request from user B for /api/conversations/N/messages/all, /messages/count or /timeline is served from the cache and findByIdAndUser never runs. Conversation ids are sequential Longs, so they are easy to enumerate. This is a cross-tenant read of full message history (ConversationController lines 40-43 and 92-104).
- **Fix:** Include the principal in the key, e.g. key = "T(org.springframework.security.core.context.SecurityContextHolder).getContext().getAuthentication().getName() + ':' + #conversationId" (the same pattern conversationList already uses), or move the ownership check to the controller before the cached call.
- **Effort:** S

#### COR-2: Text-to-SQL user scoping is a string-contains check and the table whitelist misses comma joins
- **Location:** `src/main/java/com/joshfouchey/smsarchive/service/TextToSqlService.java:41-43, 128-140, 189-199`
- **Dimension:** Correctness · **Also reported as:** OBS-2 · **Confidence:** High
- **What:**

  ```
  if (!safeSql.contains(userId.toString())) { safeSql = injectUserIdFilter(safeSql, userId); }
  validateSql(safeSql);
  ...
  TABLE_REF = "(?i)(?:FROM|JOIN)\\s+(?:`|#|\"|\\w+\\.)?([\\w]+)"
  ```
- **Why it matters:** SQL generated by the LLM, or SQL posted directly to /api/qa/sql/run (QaController lines 47-59), only has to mention the caller's UUID somewhere. So `WHERE user_id='<me>' OR true`, or a UNION/subquery over another user's rows, passes. The whitelist regex only captures the first identifier after FROM/JOIN, so `FROM messages m, users u` lets the query read users.password_hash. The read-only transaction stops writes but does not stop cross-tenant reads.
- **Fix:** Enforce scoping in the database instead of with string checks. Options: run the query as a restricted DB role with row-level security policies on user_id; or wrap it, e.g. `WITH messages AS (SELECT * FROM messages WHERE user_id = ?), contacts AS (...), conversations AS (...) <user sql>` with schema-qualified base tables made unreachable. At minimum, parse with JSqlParser and walk every FromItem/Table.
- **Effort:** M

#### COR-3: deleteImage has no ownership check and deletes the entire parent message
- **Location:** `src/main/java/com/joshfouchey/smsarchive/service/MediaService.java:46-68`
- **Dimension:** Correctness · **Confidence:** High
- **What:**

  ```
  Optional<MessagePart> opt = partRepo.findById(id);
  ...
  try { Files.deleteIfExists(originalPath); } ...
  if (part.getMessage() != null) { messageRepository.deleteById(part.getMessage().getId()); }
  partRepo.delete(part);
  ```
- **Why it matters:** Any authenticated user can DELETE /api/media/images/{id} (MediaController:60) for another user's part id. That deletes the file, the thumbnail and the whole message, including other parts and text. There is no @Transactional. Files are removed before the DB delete, so a DB failure leaves rows pointing to missing files. partRepo.delete(part) then runs on a part the message cascade has already removed.
- **Fix:** @Transactional; load with a user-scoped query (e.g. `where p.id=:id and p.message.user=:user`) and return 404 otherwise. Remove only the part (message.getParts().remove(part) with orphanRemoval), or delete the message only when it has no other parts or body. Delete files in TransactionSynchronization.afterCommit.
- **Effort:** S

#### COR-4: Contact ownership check uses User identity equality; it fails in prod once the currentUser cache is warm
- **Location:** `src/main/java/com/joshfouchey/smsarchive/service/ContactService.java:55-61, 74-85`
- **Dimension:** Correctness · **Confidence:** High
- **What:**

  ```
  var user = currentUserProvider.getCurrentUser();   // @Cacheable("currentUser") -> detached instance
  var contact = contactRepository.findById(contactId)...
  if (!contact.getUser().equals(user)) {      // User has no equals(); LAZY proxy
      throw new java.util.NoSuchElementException();
  }
  ```
- **Why it matters:** User does not override equals/hashCode (model/User.java). CurrentUserProvider caches the User entity for 15 minutes, so from the second request onward getCurrentUser() returns a detached instance from an earlier persistence context. contact.getUser() is a LAZY Hibernate proxy or a different managed instance, so identity equals is false. Rename returns 404 and merge returns 400 'Contacts do not belong to current user' for the owner. Tests miss this because application-test.yml disables caching.
- **Fix:** Compare ids: `if (!contact.getUser().getId().equals(user.getId()))` (proxy getId() does not initialize). Better, use user-scoped lookups (`findByIdAndUser`). Also consider caching only the user id/username rather than the entity.
- **Effort:** S

#### COR-5: Per-message retry after a failed batch reuses entities with stale IDENTITY ids, so messages are silently dropped
- **Location:** `src/main/java/com/joshfouchey/smsarchive/service/ImportService.java:371-405`
- **Dimension:** Correctness · **Confidence:** Medium
- **What:**

  ```
  try { messageRepo.saveAll(batch); ... }
  catch (DataIntegrityViolationException | ObjectOptimisticLockingFailureException e) { ... }
  for (Message msg : batch) {
      try { messageRepo.save(msg); saved++; }
      catch (DataIntegrityViolationException ex) { skippedDuplicates++; ... }
      catch (Exception ex) { log.error("Failed to save message", ex); failed++; }
  ```
- **Why it matters:** With IDENTITY generation, the messages persisted before the failing row already have ids set, and rollback does not reset them (hibernate.use_identifier_rollback=false). On retry, save() sees a non-null id and calls merge(). In Hibernate 6.6+/7 that throws an optimistic-lock StaleObjectStateException for a missing row, so it lands in catch(Exception): non-duplicate messages are counted as failed and lost while the import reports COMPLETED. The batch can fail even after DuplicateDetector passes, because the V7 unique index (conversation_id, md5(body), timestamp, direction, user_id) uses a different key from DuplicateDetector (protocol/msgBox, lower(trim(body))), and isDuplicate returns false on errors.
- **Fix:** Before the retry loop, reset generated state: `msg.setId(null); msg.getParts().forEach(p -> p.setId(null));` (or rebuild the entities), then insert each with persist in its own transaction (REQUIRES_NEW / TransactionTemplate). Better still, insert with `INSERT ... ON CONFLICT ON CONSTRAINT unique_message_per_conversation DO NOTHING`, and align DuplicateDetector's key with the index.
- **Effort:** M

#### COR-6: Uploaded multi-GB temp files are never deleted
- **Location:** `src/main/java/com/joshfouchey/smsarchive/controller/ImportController.java:20-35`
- **Dimension:** Correctness · **Also reported as:** RES-2 · **Confidence:** High
- **What:**

  ```
  Path tmp = Files.createTempFile("sms-stream", ".xml");
  ... transfer upload to tmp ...
  importService.startImportAsync(tmp ...);
  ```
- **Why it matters:** Nothing deletes tmp after the async import completes or fails, or when startImportAsync throws (e.g. TaskRejectedException). Each SMS Backup XML can be several GB, so repeated uploads fill the container's /tmp volume until imports and the DB fail.
- **Fix:** Delete in the import task's finally block (or via the existing completion callback used by the directory watcher), and in a catch around startImportAsync: `catch (RuntimeException e) { Files.deleteIfExists(tmp); throw e; }`.

#### COR-20: Media files (private MMS photos/videos) are served without authentication
- **Location:** `src/main/java/com/joshfouchey/smsarchive/config/SecurityConfig.java:64-68`
- **Dimension:** Correctness (security) · **Confidence:** High
- **What:** `/media/**` is in the permitAll list (`"/media/**", // static media (TODO: secure with token-based access)`) and WebConfig maps `/media/messages/**` straight to the media root. nginx proxies `/media` to the app. Anyone who can reach the frontend and knows or guesses a filename (`msg-<seq>-<epochSeconds>-<8 hex>-<n>.jpg`) gets the file, with no token and no user check.
- **Why it matters:** This is the only path where private content is reachable with no authentication at all. It bypasses user isolation too, since any user's files can be fetched. Exposure depends on whether the reverse proxy is reachable from outside the LAN.
- **Fix:** Serve media through an authenticated controller that checks part ownership (`MessagePart` → `message.user`), using `ResourceRegion` for range support. Or keep static serving, but require a short-lived signed URL (`?exp=..&sig=HMAC(path|exp|userId)`) that a filter verifies. The `<img>` tags in the frontend cannot send the Authorization header, which is why the TODO exists: signed URLs or a cookie-scoped media token solve that.
- **Effort:** M

#### PERF-1: Keyword search OR's an unindexable trigram similarity() predicate, forcing per-row scans (page + count query)
- **Location:** `src/main/java/com/joshfouchey/smsarchive/repository/MessageRepository.java:83-187`
- **Dimension:** Performance · **Confidence:** High
- **What:**

  ```
  WHERE m.user_id = :userId AND (
    to_tsvector('english', COALESCE(m.body,'')) @@ plainto_tsquery('english', :text)
    OR similarity(COALESCE(m.body, ''), :text) > 0.25 )
  ... ORDER BY ts_rank(...) * 0.5 + similarity(COALESCE(m.body,''), :text) * 0.5
  ```
- **Why it matters:** still open from 2026-06-27 review. similarity(expr, :text) > 0.25 is a function call, not the % operator, so the GIN gin_trgm_ops index (V8, on raw body, not COALESCE(body,'')) can never be used; the OR also defeats the FTS GIN bitmap. Every /search/text, unified keyword and Q&A search does to_tsvector + similarity on all ~200k rows of the user, twice (Page count query repeats the WHERE). Seconds per keystroke-triggered search.
- **Fix:**

  ```
  Use the indexable operator on the indexed expression and split the OR into a UNION:
  SET LOCAL pg_trgm.similarity_threshold = 0.25;
  SELECT id FROM messages WHERE user_id=:u AND to_tsvector('english',coalesce(body,'')) @@ q
  UNION
  SELECT id FROM messages WHERE user_id=:u AND body % :text
  and return Slice instead of Page (or cap count).
  ```
- **Effort:** M

#### PERF-3: Import resolves conversation and merges last_message_at per message (3-6 DB round-trips/message)
- **Location:** `src/main/java/com/joshfouchey/smsarchive/service/importpipeline/ConversationAssigner.java:30-89`
- **Dimension:** Performance · **Confidence:** High
- **What:**

  ```
  Conversation convo = conversationService.findOrCreateOneToOneForUser(...);
  updateConversationLastMessage(convo, msg);
  ...
  if (convo.getLastMessageAt() == null || msg.getTimestamp().isAfter(convo.getLastMessageAt())) {
      convo.setLastMessageAt(msg.getTimestamp());
      conversationService.save(convo);
  }
  ```
- **Why it matters:** Each message runs its own @Transactional findOrCreate (contact lookup + findByUserAndSingleParticipant join with size() subquery), then save() merges a detached Conversation with CascadeType.MERGE on participants (SELECT conv+participants, UPDATE). Backups are ascending by date, so the update fires for nearly every message. 200k messages -> ~1M round-trips, dominating import time.
- **Fix:**

  ```
  Per-import cache: Map<String threadKey, Conversation> convCache; track Map<Long convId, Instant maxTs> in memory; at each batch flush run one
  UPDATE conversations SET last_message_at = GREATEST(COALESCE(last_message_at,'-infinity'), v.ts) FROM (VALUES ...) v(id,ts) WHERE id = v.id
  ```
- **Effort:** M

#### PERF-4: Duplicate detection: one EXISTS query per message plus O(n) in-batch scan and unbounded seenKeys of full bodies
- **Location:** `src/main/java/com/joshfouchey/smsarchive/service/importpipeline/DuplicateDetector.java:39-110`
- **Dimension:** Performance · **Confidence:** High
- **What:**

  ```

  if (seenKeys.contains(key)) ...
  boolean exists = messageRepo.existsByConversationAndTimestampAnd...(...);
  ```
- **Why it matters:** still open from 2026-06-27 review. Index-backed (idx_messages_dedupe_prefix) but still a network round-trip per message; re-importing cumulative backups is mostly duplicates so this is the hot loop. isDuplicateInBatch is redundant with seenKeys; seenKeys keeps every lowercased body for the whole multi-GB import.
- **Fix:** Rely on the unique index: INSERT ... ON CONFLICT DO NOTHING via JdbcTemplate.batchUpdate per batch, or one batched lookup per batch: SELECT conversation_id, timestamp, md5(body) FROM messages WHERE (conversation_id,timestamp) IN (...). #### RES-1: One 120s timeout for chat and query embedding, multiplied by SDK retries and app retries, on the default search path
- **Location:** `src/main/resources/application.yml; src/main/java/com/joshfouchey/smsarchive/service/SemanticSearchService.java; src/main/java/com/joshfouchey/smsarchive/service/UnifiedSearchService.java:application.yml:81; SemanticSearchService.java:90-95,180-205; UnifiedSearchService.java:73,277-286`
- **Dimension:** Resilience · **Confidence:** High
- **What:**

  ```
  spring.ai.openai.timeout: 120s applies to both chat and embedding. Spring AI 2.0.2's OpenAiChatModel and OpenAiEmbeddingModel do NOT use the spring.ai.retry RetryTemplate (verified in the jar sources; that template's maxAttempts=10 has no effect here). They pass spring.ai.openai.max-retries to the openai-java 4.80 RetryingHttpClient. That defaults to 3 (AbstractOpenAiOptions.DEFAULT_MAX_RETRIES), so 4 attempts. The client retries IOException/timeouts, 408, 409, 429 and 5xx, with 0.5–8s backoff. SemanticSearchService.embedQueryWithRetry then wraps this in 2 more attempts plus a 1s sleep:
    for (int attempt = 0; attempt < 2; attempt++) { embeddingService.embedQuery(query) ... Thread.sleep(1000) }
  The default SearchMode is AUTO, which runs hybridSearch. Hybrid always calls semanticSearchService.search on the Tomcat request thread.
  ```
- **Why it matters:** Search is the main hot path. If the embed server hangs (model loading, GPU busy with chat), one search request can block for about 2 × 4 × 120s ≈ 16 min before falling back to keyword-only. If it is simply down (connection refused), every search still pays about 8s (SDK backoff 0.5+1+2s, twice, plus the 1s sleep) before degrading. Graceful degradation exists but triggers far too late, and the browser has already got an nginx 504 at 60s (see RES-5).
- **Fix:**

  ```
  Use a short, low-retry budget for interactive embeddings and keep 120s only for chat/batch:
  spring.ai.openai:
    max-retries: 1
    embedding.options... (or build a dedicated query OpenAiEmbeddingModel with timeout(Duration.ofSeconds(5)), maxRetries(0))
  Drop the extra app-level loop in embedQueryWithRetry, or skip it when the cause is a timeout. Optionally add a 30s 'embedding down' flag after a failure so hybrid search goes straight to keyword-only.
  ```
- **Effort:** S

#### OBS-1: Test suite never gates a release: image build skips tests and CI has no test job
- **Location:** `Dockerfile; .github/workflows/docker-images.yml:Dockerfile:17-18; docker-images.yml:3-12,37-`
- **Dimension:** Testing & Observability · **Confidence:** High
- **What:** The backend image is built with `./gradlew clean bootJar -x test`. The only workflow (docker-images.yml) runs on every push to master, builds the images, and pushes `latest` to GHCR. It has no `./gradlew test` step. No coverage tool (jacoco) is configured in build.gradle.
- **Why it matters:** The 41 test classes (about 152 tests) only run when someone runs them locally. A regression in the import pipeline, auth, or dedup can reach the `latest` image that the home server pulls. This makes every other test in the repo advisory only.
- **Fix:** Add a `test` job to docker-images.yml (ubuntu-latest has Docker, so Testcontainers works) that runs `./gradlew test`. Make the build matrix depend on it with `needs: test`. Publish build/reports/tests on failure. Optionally add the jacoco plugin with a jacocoTestReport task so coverage of service/ and controller/ is visible. Keep `-x test` in the Dockerfile only once CI gates the image.
- **Effort:** S

#### OBS-3: User-isolation tests cover one endpoint; several job/admin endpoints have no ownership check and no test
- **Location:** `src/main/java/com/joshfouchey/smsarchive/controller/ImportController.java:32-35 (also SemanticSearchController.java:88-91 + EmbeddingService.java:404-406, MediaJobController.java:54-56, SecurityConfig.java:66, ConversationMaintenanceController.java:26-)`
- **Dimension:** Testing & Observability · **Also reported as:** COR-19 · **Confidence:** High
- **What:**

  ```
  UserIsolationTest has a single test, and it only checks GET /api/messages/contacts. Several endpoints have no ownership check:
  - ImportService.getProgress(UUID): GET /import/progress/{id} returns any job's progress.
  - EmbeddingService.cancelJob(jobId): POST /api/search/embeddings/cancel/{jobId} lets any user cancel any job.
  - MediaJobController.getJobStatus: returns any thumbnail job.
  - /api/admin/conversations/*: ConversationMaintenanceService runs global UPDATE/INSERT across all users for any authenticated user.
  - /media/** is permitAll, so media files are served without a token. MediaControllerTest only checks 404s with @WithMockUser.
  No test covers conversations/{id}/messages, search, semantic search, gallery, or contact merge with another user's token.
  ```
- **Why it matters:** Per-user isolation is the main security invariant of a multi-user archive. Gaps already exist, and nothing would catch new ones introduced in hot read paths.
- **Fix:** Extend UserIsolationTest, which already registers uA and uB with real JWTs, into a parameterized matrix. For each user-scoped GET or POST (conversations/{A's id}/messages, /messages/count, /timeline, /api/messages/{id}/context, /search/text, /api/search/unified, /api/media/images?contactId=A's, POST /api/contacts/{A}/merge/{A2}, DELETE /api/conversations/{A}, PATCH name), assert 403/404 or empty results for token B. Add cases for import progress, embedding cancel or status, and thumbnail job status by another user's job id, expecting 404. Add an anonymous GET /media/messages/<existing file> case that documents the intended policy. Add an admin-maintenance case asserting that user B cannot mutate user A's conversations.
- **Effort:** M

#### COR-8: Find-or-create races: the catch-and-requery fallback can't work inside @Transactional, and conversations have no unique constraint
- **Location:** `src/main/java/com/joshfouchey/smsarchive/service/ConversationService.java:454-480 (callers 420-440)`
- **Dimension:** Correctness · **Confidence:** High
- **What:**

  ```
  try { return contactRepository.save(c); }
  catch (DataIntegrityViolationException e) {
      return contactRepository.findByUserAndNormalizedNumber(user, normalizedNumber).orElseThrow();
  }
  ```
- **Why it matters:** findOrCreateContact is called from @Transactional findOrCreateOneToOneForUser/findOrCreateGroupForUser. After the unique violation, PostgreSQL aborts the transaction, so the requery fails with 'current transaction is aborted' and Spring has marked the transaction rollback-only (UnexpectedRollbackException). ## Positive observations

- **Import pipeline:** a hardened StAX parser (DTDs and external entities disabled) streams multi-GB files without buffering. The `ThreadLocal` import context is cleared in `finally`. Unexpected persistence errors fail the job instead of reporting COMPLETED. Re-imports are idempotent thanks to in-run `seenKeys`, DB duplicate detection and `unique_message_per_conversation`.
- **Read paths:** two-query id-page-then-fetch avoids Hibernate's in-memory pagination. A LATERAL last-message query drives the conversation list. `default_batch_fetch_size: 50` and `@BatchSize` keep lazy loads batched, and page sizes are capped at 500.
- **Text-to-SQL defense in depth:** queries run in a `READ ONLY` transaction with a 10 s statement timeout, a row cap, single-statement rejection, and a bounded executor. The scoping check is weak (COR-2), but the blast radius stops at reads.
- **Graceful degradation:** semantic/hybrid search falls back to keyword results when embeddings fail, and query embeddings are cached (fixed since the 2026-06-27 review, along with per-query `ef_search` and moving text-to-SQL off the common ForkJoin pool).
- **Job hygiene:** embedding jobs are persisted, and RUNNING/PENDING jobs left over from a restart are reset on startup. Embedding upserts use `ON CONFLICT`.
- **Tests:** they run on a Testcontainers `pgvector:pg18` image matching prod, not H2. `AuthIntegrationTest` covers token confusion and garbage tokens. There are meaningful import regression tests, and `RestExceptionHandlerTest`/`MediaControllerTest` pin the earlier media log-loop fix.
- **Ops:** Compose caps logs, wires health checks with `depends_on: service_healthy`, sets Hikari leak detection, and Boot 4's default graceful shutdown is in effect.
